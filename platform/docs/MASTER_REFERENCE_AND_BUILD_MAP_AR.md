# الحازم سمارت — المرجع الموحد وخريطة ربط الوثيقة بالمشروع

**المرجع الحاكم:** وثيقة الحازم سمارت، الإصدار المرجعي 1.0، 17 أكتوبر 2026.  
**نسخة المشروع محل المطابقة:** v9.1 / نسخة عمل المرحلة الثانية.  
**الغرض:** تحويل متطلبات الوثيقة إلى سجل تنفيذ قابل للتتبع، دون حذف أي صفحة أو وظيفة أو اعتبار وجود الكود دليلًا على اكتمالها.

## 1. قواعد حاكمة

1. الوثيقة المرجعية هي مصدر متطلبات المنتج والهوية والنطاق؛ والكود الفعلي هو مصدر معرفة ما هو موجود تقنيًا.
2. لا تُحذف صفحة أو مسار أو جدول أو وظيفة قائمة دون موافقة صريحة وتحليل أثر موثق.
3. لا يُعلن اكتمال أي متطلب إلا بعد الاختبار وتسجيل الدليل.
4. البيانات التجريبية أو غير الموثقة لا تعرض على أنها حقيقية.
5. قاعدة البيانات مصدر الحقيقة؛ وتغييراتها عبر migrations مراجعة وغير مدمرة.
6. الذكاء الاصطناعي مساعد؛ لا يخترع المنتجات والأسعار والضمانات ولا ينفذ عمليات إدارية حساسة ذاتيًا.
7. لا نشر إنتاجي قبل اجتياز اختبارات القبول الحرجة والعالية أو توثيق استثناء مقبول.

الأجهزة الكهربائية، التكييفات، الأدوات المنزلية، النجف والإضاءة والتحف.

## 5. ربط الخدمات وواجهات API

| المسار | الوظيفة | ملاحظات التحقق |
|---|---|---|
| `GET /api/catalog` | قراءة الكتالوج والعروض | اختبار النشر والمصادر وRLS والصفحات الكبيرة |
| `POST /api/ai` | مستشار/موظف ذكي | لا يقدم حقيقة منتجية دون استرجاع موثق من الكتالوج؛ اختبار حدود الطلبات والتكلفة والمهلة |
| `POST /api/sales-leads` | تسجيل طلب تواصل | اختبار مكافحة الإغراق والتحقق من المدخلات وخصوصية القراءة |
| `/api/admin/catalog/*` | إدارة المنتجات والماركات والصور | اختبار أدوار الإدارة ورفع الملفات والتحقق من نوع الملف الفعلي |
| `/api/merchant/*` | طلب انضمام تاجر ومراجعته | اختبار حالات الطلب وعدم تمكين التاجر من اعتماد نفسه |
| `/api/seller/*` | إدارة عرض المتجر والعروض | اختبار أن التاجر يدير سجلاته فقط وأن السعر المرسل ليس سعرًا متحققًا مستقلًا |
| `/api/admin/sales-leads/*` | إدارة متابعة العملاء | اختبار الدور وسجل التدقيق ورفض التحديث المباشر غير المصرح |
| `/api/admin/ai-workforce` | إدارة وكلاء الذكاء الاصطناعي | اختبار صلاحيات الإدارة وتغيير التعليمات وسجل التدقيق |

## 6. قاعدة البيانات والترحيلات

الترحيلات الموجودة في نسخة العمل: `001_core.sql` إلى `005_sales_lead_input_hardening.sql`، بالإضافة إلى seed مرجعي.

قبل أي تغيير:
- مراجعة المخطط والعلاقات والقيود الحالية.
- نسخ احتياطي واختبار migration في staging.
- عدم حذف أو دمج سجلات تلقائيًا.
- اختبار RLS بحسابات anonymous وUSER وVIEWER وEDITOR وMANAGER وADMIN، مع اختبار البائع المعلق والمعتمد عند انطباقه.
- التحقق من صلاحيات الدوال وRPC وStorage.

**غير مثبت:** لا يوجد في مساحة العمل اتصال حي بمشروع Supabase؛ لذلك لم تُثبت الترحيلات أو سياسات RLS في قاعدة فعلية.

## 7. نموذج الثقة والأسعار

يجب أن يكون السعر كيانًا منفصلًا مرتبطًا بالمنتج ويحتوي القيمة والعملة والنوع والمصدر والرابط وتاريخ الرصد وحالة التحقق والصلاحية إن توفرت.

| نوع السعر | العرض المطلوب |
|---|---|
| سعر رسمي | مصدر رسمي وتاريخ رصد |
| سعر الحازم | فقط عند صدوره فعليًا عن الشركة |
| سعر سوق موثوق | المصدر والتاريخ وحالة التحقق |
| سعر غير متحقق | وسم صريح؛ لا يظهر كسعر مؤكد |
| بيانات ناقصة | «غير متاح في مصدر موثوق حاليًا» |

يجب التمييز بين `priceUpdatedAt` و`priceVerifiedAt`. إدخال التاجر للسعر لا يساوي التحقق المستقل منه.

## 8. الأدوار والأمان والخصوصية

الأدوار المرجعية: USER وVIEWER وEDITOR وMANAGER وADMIN. إذا اختلفت الأدوار في النظام الحالي، تُراجع التوافقية قبل أي تعديل.

متطلبات أساسية:
- صلاحيات الخادم وقاعدة البيانات، لا إخفاء الأزرار فقط.
- منع وصول العميل إلى بيانات عميل آخر.
- موافقة تسويقية صريحة قابلة للإلغاء.
- موافقة منفصلة اختيارية لبيانات المناسبات والتذكير.
- عدم تسجيل كلمات المرور أو الأسرار في سجل التدقيق.
- Audit Log للفاعل والعملية والسجل والتوقيت والنتيجة.
- خمس حالات متتالية متطابقة موثقة قبل نشر حكم نهائي عن مشكلة متكررة؛ وما دون ذلك مؤشر داخلي.

## 9. قائمة الاختبارات ومعايير القبول

لكل اختبار إحدى الحالات: **ناجح / فاشل / لم يُختبر**، مع دليل وتاريخ وبيئة الاختبار.

1. جميع الصفحات والمسارات: فتح وتسجيل أخطاء التحميل.
2. الصلاحيات: السماح والرفض حسب الدور.
3. RLS: القراءة والكتابة بحسابات متعددة.
4. المنتجات: إنشاء وتعديل ونشر في staging.
5. التكرار: كشف فقط دون حذف تلقائي.
6. البحث: نتائج موجودة وغير موجودة وبيانات ناقصة.
7. المستشار والمقارنة: الميزانية والاحتياج والمصادر ومنع الاختلاق.
8. حاسبة التكييف: القيم الفارغة والسالبة والكبيرة والوحدات والحدود؛ لا تخلط مع حاسبة استهلاك الكهرباء.
9. الاتصال: روابط الهاتف وواتساب دون إجراء اتصال حقيقي.
10. الإدارة: الأدوار وسجل التدقيق وجودة البيانات.
11. الأداء: الاستعلامات والصور والاستجابة وPagination.
12. التوافق: هاتف 430px، لوحي، حاسوب، RTL والعربية.
13. البناء: `npm ci`, `npm run lint`, `npm run build` والاختبارات المتاحة.
14. النشر: لا يتم قبل مراجعة النتائج والبيانات.

## 11. أولويات العمل المباشرة على v9.1

### P0 — قبل أي إطلاق عام
- إكمال تأمين AI وطلبات العملاء بمحدد طلبات مشترك في بيئة الإنتاج.
- تأكيد إعدادات الاتصال الرسمية وتوحيدها مركزيًا.
- تشغيل تثبيت نظيف وفحص TypeScript والبناء والاختبارات.
- اختبار RLS وصلاحيات الإدارة وطلبات العملاء في Supabase staging.

### P1 — قبل اعتماد الوظائف الأساسية
- تصحيح دلالة التحقق من السعر في كل الواجهات والـ APIs.
- استكمال نموذج الأسعار المنفصل إن لم يكن موجودًا في المخطط الفعلي.
- استكمال توثيق المصدر لكل منتج وصورة ومواصفة وضمان.
- مراجعة رفع الصور وفحص المحتوى الفعلي للملفات.
- إعداد سجل تدقيق شامل للعمليات الحساسة.

### P2 — استكمال نطاق الوثيقة
- صفحات العلامات التفصيلية والكتالوجات الرسمية.
- AUX والتكييفات وحاسبة قدرة التكييف.
- المحتوى والأكاديمية والأسئلة الشائعة والشفافية والمجتمع.
- CRM والشكاوى وخدمة ما بعد البيع وجودة البيانات وإعدادات الموقع.
- SEO وصفحة 404 واختبارات RTL والاستجابة.

## 13. تقرير التسليم الإلزامي لكل دفعة

- ما نُفذ فعلًا مع الأدلة.
- قائمة الملفات التي تغيرت.

## 14. القرار التنفيذي

هذه الوثيقة خريطة ربط تشغيلية للمرجع الشامل، وليست ادعاءً بأن جميع الوظائف أصبحت جاهزة. نسخة v9.1 الحالية تحتوي أساسًا تقنيًا لبعض وظائف الكتالوج والمقارنة والمبيعات والتجار والموظفين الافتراضيين؛ وتبقى وظائف كثيرة غير مكتملة أو غير مختبرة. يستمر البناء على المشروع الحالي، مع الاحتفاظ بكل المسارات والبيانات، ولا يُعلن القبول النهائي قبل إغلاق العيوب الحرجة والعالية وتوثيق الأدلة.

## تحديث التنفيذ — v10 workstream

تمت إضافة مسارات مرجعية مستقلة للأقسام التي كانت غير ممثلة بمسارات في نسخة العمل: العروض، الأخبار، النصائح، الأكاديمية، الشفافية، AUX، التكييفات، المطبخ الذكي، الإضاءة والتحف، الأسئلة الشائعة، نادي الحازم، المجتمع، الدعم، الملف الشخصي، وحاسبة قدرة التكييف. هذه صفحات حالة تجهيز وليست إعلانًا عن اكتمال الوظائف.

أضيفت إعدادات هوية واتصال مركزية في `lib/config/site.ts` بقيم الوثيقة: الهاتف 01050509779 وواتساب 01044111143. أُضيفت صفحة 404 فعلية وملفات SEO الأساسية، كما أصبح AUX مباشرة قبل Footer في الصفحة الرئيسية. أضيف مسار داخلي لكل علامة تجارية مسجلة.

**ما لم يثبت بعد:** البناء الكامل، تكامل Supabase الحي، RLS، مصادقة جميع الأدوار، تدفقات إدارة المحتوى، CRM، حاسبة قدرة التكييف الرقمية، ومصادر الكتالوج والأسعار. راجع `docs/PHASE_EXECUTION_LOG.md` لحالة كل مرحلة.
